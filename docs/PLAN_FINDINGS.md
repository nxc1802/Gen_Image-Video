# Master Plan technical findings

These findings supplement `MASTER_PLAN.md`; they do not edit its architecture or authorize skipping phase gates.

## Phase 5 — exact backend limits and Enhancement scope

- **Problem/cause:** The pinned Enhancement suite contains only the Real-ESRGAN x4plus checkpoint. RIFE and audio enhancement weights are absent, and all four manifest capabilities are explicitly disabled. Implementing these as active generic external-URL proxies would break the manifest/checkpoint rules.
- **Impact/proposal:** Complete the actual ComfyUI Real-ESRGAN backend path for the pinned file, preserve DISABLED state/public rejection, and use an isolated exact-checkpoint implementation probe to exercise it without production activation. Leave unbacked capabilities explicitly unsupported. RIFE/audio need separate canonical checkpoint identities before implementation/enablement. No checkpoint substitution or artificial output is acceptable.
- **Other corrected integration assumptions:** Qwen Image 2.1 requires 64-channel input latents; adapter-owned latent construction replaces legacy 4-channel graph assumptions. MiniMax uses the current AV conditioning nodes and native 17k+5 frame grid; old named placeholder nodes are not accepted as working inference. Backend node availability is checked before executing the selected graph. Wan uses text/image pipeline wrappers sharing the same exact components, not alternate checkpoints/backends. Extension concatenation failure is terminal, rather than returning an unstitched segment.
- **Speech:** The selected Qwen TTS Base checkpoint requires reference audio/transcript; built-in preset voices require another explicitly chosen checkpoint. There is no CustomVoice/VoiceDesign fallback.
- **YuE2:** The actual upstream package uses `YuE2Pipeline`, not a bare language-model generation call. It remains BLOCKED on T4 for the selected BF16 runtime. Its VAE path is fixed to the manifest bundle; no automatic precision/model fallback is introduced.
- **Disposition:** Recorded before native execution and final gate. These are explicit fail-closed implementation limits, not permission to skip validation or claim production readiness. Native implementation probes do not substitute for Phase 8/9 gates.

## 2026-11-12 — Decisions now has an official OpenAI API

- **Problem:** Master Plan §§2.2/33 classify `POST /v1/decisions` as a custom endpoint. The current [official OpenAI API reference](https://developers.openai.com/api/reference/resources/decisions/methods/create) defines that endpoint with `model`, `input`, `questions`, typed answers and usage.
- **Cause:** The plan's custom-endpoint inventory is behind the upstream API. This is a contract classification issue; the generic DecisionEngine architecture remains feasible.
- **Impact:** Treating the old single-task Factory envelope as the final public contract would conflict with the plan's stronger requirement to prefer OpenAI compatibility wherever a corresponding capability exists. The old service also describes token logprobs and ECE/Brier calibration metrics that the actual [vLLM protocol](https://github.com/vllm-project/vllm/blob/main/vllm/entrypoints/openai/decisions/protocol.py) does not return. Native score is an expected zero-based level index, not a numeric level label.
- **Proposal for Phase 6:** Make the public endpoint accept/return the official OpenAI Decisions shape for the supported text-only subset. Reject unsupported input/question types explicitly. Keep any legacy normalization separate from the public contract and verify the official SDK using a local `base_url`. Do not rename or replace the selected checkpoint/backend, or invent missing calibration/logprobs.
- **Current action in Phase 5:** Implement the manifest-selected native adapter and validate actual typed backend answers. Preserve predicate probability and native score; expose a legacy numeric-scale conversion separately as an explicitly derived value. Preserve real usage, refusals and input order. The canonical public API migration remains pending Phase 6; no OpenAI-hosted API call or official SDK acceptance has occurred.
- **Disposition:** Recorded before implementation. The proposal follows the user's existing OpenAI-first rule; it does not require a new architecture or change the phase order. Phase 6 must resolve this finding before declaring its compatibility gate passed.

## Phase 8 Wave D: Wan wrapper silently widens shared weights

Keep the exact checkpoint, backend, GPU0 assignment, CPU offload and original semantic thresholds. Add benchmark-only startup RAM/cgroup/exit diagnostics to distinguish future process deaths.
